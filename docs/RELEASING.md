# Releasing RivetMSP

## Branches

| Branch | Channel | Purpose |
|---|---|---|
| `master` | Production | What production servers run. Only ever moves by fast-forward from `beta`. |
| `beta` | Beta | Where work lands first. Beta-channel servers follow it (Administration > Update). |

Short-lived feature branches are merged into `beta` (pull request or merge) and deleted afterwards. Nobody pushes
directly to `master`, and it is never force-pushed or deleted. Protect it on GitHub (Settings > Branches: block force
pushes and deletions; ideally require a pull request).

## Cutting a release

1. Everything is on `beta` and tested on a beta server. `CHANGELOG.md` has the release heading (the `[Unreleased]`
   section is renamed) and `includes/app_version.php` holds the same version.
2. Fast-forward production to beta (this must be a pure fast-forward; if it is refused, merge `master` into `beta` first):

       git fetch origin
       git checkout master && git merge --ff-only origin/beta && git push origin master

3. Tag that commit and push the tag (annotated): `git tag -a vYY.MM.N -m "Release YY.MM.N" && git push origin vYY.MM.N`.

## Tags

- Format `vYY.MM.N` (for example `v26.10.16`); a beta pre-release, if needed, is `vYY.MM.N-beta.K`.
- Older `v1.x`/`v2.x`-style tags are legacy. Keep them: Administration > Update shows `git describe` and servers may be
  pinned to them.
- Never tag a commit a live server is running except as part of a release above, and never move or delete a published tag.
  `git describe` on the Update page reads the nearest tag, so a stray tag changes what every server reports.

## Vendor files

`vendor/composer/*` is regenerated by `composer install` and records the checkout's git HEAD, so it differs on every
server. Never commit it from a server checkout. The in-app Update and `deploy/update.sh` reset it
(`git checkout -- ':/vendor/composer'`) before pulling.
